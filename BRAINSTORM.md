# Entre Nous — conception

Presse-papier et fichiers partagés entre les appareils d'une même personne (Mac, Android,
Linux, Windows, iPhone, navigateur), chiffrés de bout en bout, sans ouvrir de port sur la box.
Ce document garde les choix structurants et ce qui est réellement implémenté ;
`README.md` donne les commandes.

## 1. Principes

- Bidirectionnel, entre **appareils égaux** d'un même groupe (Mac ↔ téléphone, téléphone ↔ téléphone).
- Mac : appli de barre des menus, toujours active.
- Téléphone : PWA, connectée **uniquement au premier plan** (batterie, vie privée).
- Appairage (et installation de la PWA) par QR code. Plusieurs groupes indépendants.
- Fonctionne partout sans configuration réseau : tout passe par un relais en HTTPS.
- Le relais ne peut rien lire et ne garde rien sur disque.

## 2. Décisions structurantes

| Sujet | Décision |
|---|---|
| Architecture | Cœur TypeScript commun ; PWA (Android, iOS, navigateurs) ; Mac = Swift + WKWebView ; Linux et Windows = Tauri (§8 ter) ; Android = Capacitor ; les applis embarquent la même interface |
| Interface | Alpine.js en build CSP (pas d'`eval`), politique de sécurité stricte |
| Transport | Relais WebSocket ; WebRTC direct entre appareils du même réseau (mode local, §8 bis) |
| Hors ligne | Boîte aux lettres chiffrée sur le relais, historique partagé jusqu'à expiration |
| Rétention | Réglage du groupe, modifiable par tout membre, 24 h par défaut, plafonnée par `MAX_TTL` (7 j) ; raccourcir s'applique aussi aux éléments existants, allonger seulement aux nouveaux |
| Retrait d'un appareil | Par n'importe quel membre ; rotation des clés, l'historique suit les membres restants |
| Taille des envois | Pas de limite pour un envoi manuel ; partage automatique du Mac limité par un réglage du groupe (1 Mo par défaut, 10 Mo, 100 Mo) ; le relais est borné par `MAX_STORAGE` et `mem_limit` |
| Taille de l'historique | Réglage du groupe : 1, 10 (défaut) ou illimité ; appliquée par le relais, qui supprime les plus anciens (la note en direct ne compte pas) |
| Relais | Un conteneur Node + Redis en RAM, sans volume par défaut ; volume optionnel (`PERSIST`) |
| Adresses | Page d'accueil sur `/`, PWA sous `/app/`, appli Mac en `/download/Entre-Nous-mac.zip` ; relais public `https://entrenous.0xdba.dev` |

## 3. Cryptographie

| Brique | Choix (bibliothèques `@noble`) |
|---|---|
| Échange de clés | X25519 + ML-KEM-768 hybride (combinateur X-Wing) |
| Signatures | Ed25519 |
| Chiffrement | XChaCha20-Poly1305 |
| Dérivation | HKDF-SHA-256, étiquettes `entrenous/v1/<usage>` |

- **Pré-clés** : chaque appareil publie pour chaque groupe une pré-clé X-Wing signée,
  renouvelée chaque jour. Une ancienne pré-clé est détruite après son remplacement
  + la rétention du groupe (+1 h) : la confidentialité persistante suit la rétention.
- **Éléments** : une clé aléatoire chiffre le contenu une seule fois ; elle est enveloppée
  (construction type HPKE) pour la pré-clé de chaque membre. Les métadonnées sont signées
  par l'expéditeur.
- **En-tête chiffré** (type, nom, taille, miniature, texte court) bourré à un multiple de 256 o ;
  texte de moins de 64 Ko dans l'en-tête, au-delà envoyé comme fichier.
- **Contenus** découpés en morceaux de 1 Mio ; chaque morceau est authentifié avec son
  index, l'identifiant de l'élément et un drapeau « dernier » (ni réordonnable ni tronquable) ;
  le dernier morceau est bourré à un multiple de 64 Kio.
- **Mac** : ce qu'il écrit dans le presse-papier est marqué `org.nspasteboard.ConcealedType` ;
  il ignore ce que les gestionnaires de mots de passe marquent Concealed/Transient/AutoGenerated.

## 4. Groupes, appairage, retrait

- **Groupe** : secret de 256 bits partagé par les membres. Salle sur le relais =
  `sha256(kdf(secret, "room"))` : le relais ne voit qu'un identifiant opaque.
- **État du groupe** (membres, nom, rétention) : signé, chiffré avec `kdf(secret, "state")`,
  versionné sur le relais (compare-and-swap). Fusion : union des membres, retraits
  définitifs, nom et rétention les plus récents. Un membre ajouté pendant qu'un appareil
  était hors ligne est accepté s'il a été ajouté par un membre connu (chaîne de parrainage).
- **Appairage** : le QR contient `https://…/app/#p=<secret à usage unique>`. Le fragment
  n'est jamais envoyé au serveur et la page l'efface aussitôt. Les deux appareils se
  retrouvent sur un canal du relais dérivé du secret, et l'invitant envoie l'état du groupe
  chiffré avec une clé dérivée du même secret. Invitation valable 3 min, pour un seul appareil.
  N'importe quel membre peut inviter.
- **iOS** : une PWA installée ne partage pas le stockage de Safari ; l'appli invite donc
  à l'installer d'abord, puis à scanner depuis l'appli (scanner intégré, `jsQR`).
- **Retrait** : nouveau secret de groupe transmis par un élément « rotation » enveloppé
  pour les seuls membres restants ; l'historique est d'abord déplacé dans la nouvelle salle
  (`items.move`, pré-clés conservées pour qu'il reste lisible), puis l'ancienne salle ne garde
  que la rotation (`room.purge`). L'appareil retiré, s'il se reconnecte, s'efface lui-même.
  Un groupe réduit à un membre est dissous (`room.delete`, marqueur « dissous » 30 j).
- Les appairages vivent sur les appareils : un relais vidé ne casse aucun groupe,
  les appareils republient état et pré-clés à la connexion.

## 5. Historique et boîte aux lettres

- Un envoi = un **élément** sur le relais : métadonnées signées, en-tête chiffré,
  enveloppes, morceaux. Les membres connectés le reçoivent aussitôt, les autres à
  l'ouverture de l'appli.
- Tout l'historique reste disponible jusqu'à expiration : chaque élément peut être recopié,
  enregistré ou supprimé par n'importe quel membre.
- Les appareils ne téléchargent un contenu qu'au moment de le copier ou de l'enregistrer.
- Un élément expiré quitte l'historique local à la seconde.
- **Partage automatique du Mac** : par défaut, une copie n'est envoyée que si un autre
  appareil du groupe est connecté ; quand un appareil se connecte, la dernière copie du Mac
  lui est envoyée. Le relais connaît donc la présence (identifiants pseudonymes).
  Une copie plus grosse que la limite du groupe n'est ni lue ni envoyée : un message invite
  à passer par « Fichier ». Les envois manuels passent toujours par la boîte aux lettres.
- **À la connexion** (ouverture de l'appli, sortie de veille), le dernier élément reçu
  pendant l'absence est mis dans le presse-papier s'il a moins d'une minute (Mac, Android).
- **Suppression** : un élément (confirmation selon le réglage de l'appareil, activée par défaut),
  ou « Tout supprimer » (historique et note, pour tous les membres, toujours confirmé).
- **Réception** : le Mac et Android (au premier plan) écrivent l'élément reçu dans le
  presse-papier ; iOS exige un toucher (« Copier ») et ne permet pas l'effacement automatique.
- Tout envoi attend que la connexion soit établie et les pré-clés des membres chargées
  (sinon un partage Android, reçu pendant la connexion, n'était lisible que par l'expéditeur).

## 6. Note en direct

- Un champ texte par groupe, synchronisé à chaque frappe. C'est un élément `note` sans
  contenu : sa clé est enveloppée pour chaque membre, et chaque modification rechiffre
  tout le texte (bourré à 256 o). Le relais n'en garde que la dernière version (`note.put`),
  et la rétention repart de la dernière modification.
- Un texte vide supprime la note du relais. Un appareil arrivé après coup la reçoit quand
  son auteur la renvoie (nouvelle clé). En cas de frappe simultanée, la dernière version gagne ;
  une modification reçue pendant qu'on tape attend une pause de 1,5 s.

## 7. Contenus et plateformes

| | Envoyer | Recevoir |
|---|---|---|
| Mac, Linux, Windows | surveillance du presse-papier (texte, image, fichier copié dans le gestionnaire de fichiers), glisser-déposer | texte et image dans le presse-papier ; autre fichier écrit dans le dossier temporaire puis mis dans le presse-papier |
| Android | « Envoyer le presse-papier », « Fichier », « Partager → Entre Nous » (Web Share Target) | presse-papier si l'appli a le focus ; fichiers via la feuille de partage |
| iOS | « Envoyer le presse-papier » (bulle « Coller »), « Fichier » | toucher « Copier » ; fichiers via la feuille de partage |
| Navigateur | Ctrl+V, glisser-déposer, « Fichier » | « Copier », téléchargement |

- Mac : fichiers reçus effacés à l'expiration de l'élément ; « Enregistrer sous… » pour les garder.
- Mac : bouton **Pause** (et entrée du menu de l'icône) : le presse-papier n'est plus lu,
  les copies faites pendant la pause ne partent jamais ; l'icône passe en ⏸.
- Mac : `beginActivity` contre App Nap ; menu Édition invisible pour Cmd+A/C/V/X/Z ;
  sélecteur de fichiers natif pour le bouton « Fichier ».
- Mac : glisser un fichier (plusieurs, une image, un texte) sur l'icône de la barre des menus
  l'envoie aussitôt, sans limite de taille ni pause, et ouvre la fenêtre sur sa progression.
- Mac : notification à la réception quand la fenêtre est fermée (réglage, activé par défaut) ;
  elle n'indique que le type et l'expéditeur, jamais le contenu.
- Connexion : test de vie toutes les 20 s quand elle est silencieuse ; vérification immédiate
  à la sortie de veille du Mac et au retour du réseau.
- Espace restant sur le relais affiché dans les réglages, alerte sous 10 %.
- Envoi d'un fichier : il apparaît sur tous les appareils dès le début, avec sa progression
  (évènement `progress` du relais à chaque bloc reçu) ; « Copier » et « Enregistrer » attendent
  la fin, et la réception automatique (Mac, notification, boîte aux lettres) ne part qu'à ce
  moment-là. Sans nouveau bloc depuis 30 s : « envoi en pause ».
- Pendant un transfert : écran maintenu allumé (Wake Lock dans l'appli web, `FLAG_KEEP_SCREEN_ON`
  sur Android), mise en veille du Mac bloquée ; l'appli passée en arrière-plan ne se déconnecte
  qu'une fois le transfert fini.
- Coupure (réseau, veille) pendant un transfert : il attend le retour de la connexion puis
  reprend avec les blocs qui manquent (`chunk.have`), jusqu'à l'expiration de l'élément.

## 8. Appli Android (Capacitor)

- Même interface web, embarquée dans l'APK (comme sur Mac : le code ne vient pas du relais).
- Plugin natif `EntreNousPlugin.java` :
  - stockage chiffré par une clé AES-GCM du Keystore Android (jamais extractible),
    sauvegarde cloud et transfert entre appareils désactivés ;
  - presse-papier sans toucher, marqué sensible (pas d'aperçu) ; images via le FileProvider ;
  - « Partager → Entre Nous » (texte, fichiers), fichiers reçus proposés par la feuille de partage ;
  - liens d'invitation (App Links vérifiés par `assetlinks.json`), bouton retour,
    passage premier plan / arrière-plan (connexion seulement au premier plan).
- Compilée dans Docker (`android/build.sh`), signée par une clé gardée hors du repo,
  APK proposé sur la page d'accueil.

## 8 bis. Mode local (transferts directs)

- Deux appareils du même réseau se relient en WebRTC (canal de données) **sans STUN ni TURN** :
  seuls les candidats « hôte » existent, la liaison ne se fait donc qu'en local, jamais par un tiers.
- Mise en relation par le relais (`signal`, transmis sans être stocké), messages chiffrés avec
  une clé dérivée du secret du groupe et liés aux deux appareils (AAD `de>à`).
- Ce qui passe sur la liaison : les mêmes blocs scellés que sur le relais, servis par l'appareil
  qui a envoyé l'élément (il garde le contenu en mémoire tant qu'il est ouvert, `outbox`).
- **Automatique** (par défaut) : l'envoi part aussi sur le relais (appareils absents ou ailleurs) ;
  un appareil du même réseau télécharge en direct, même avant la fin de l'envoi. Échec de la
  liaison (autre réseau, réseau qui isole les appareils) : le relais prend le relais, sans message.
  La liaison est préparée dès qu'un élément arrive, pour ne pas attendre au clic.
- **Réseau local uniquement** (réglage du groupe) : seule l'annonce chiffrée passe par le relais,
  sans contenu ni miniature, textes compris ; le relais n'en reçoit aucun bloc. Un élément n'est
  disponible que tant que son expéditeur est ouvert sur le même réseau.
- Le transport est injecté dans le moteur (`peers.ts` + `webrtc.ts`) : les tests le remplacent
  par une liaison en mémoire (`test/local.test.ts`).
- Débit (mesuré le 2026-11-10) : une connexion WebRTC plafonne vers 16–18 Mo/s entre deux
  navigateurs, deux en parallèle montent à 31 Mo/s (trois n'apportent rien) : deux liaisons par
  appareil, les blocs vont à la moins chargée. Contrôle de flux par l'évènement
  `bufferedamountlow` (pas de minuterie, ralentie quand la page est cachée), messages de 256 Ko,
  blocs préparés en parallèle. Résultats : 22–26 Mo/s entre deux Chrome du Mac, 9,8 Mo/s du
  Pixel 6a à l'appli Mac en Wi-Fi ; par le serveur, l'envoi est limité par le débit montant de
  la connexion internet (quelques centaines de Ko/s sur une box ADSL ou VDSL).
- Vitesse affichée sur chaque transfert (serveur ou direct, envoi ou réception) et sur un
  élément en cours d'envoi ; l'expéditeur voit « ↑ … · en direct vers <appareil> ».

## 8 ter. Applis Linux et Windows (Tauri)

- Même interface web, embarquée (le code ne vient pas du relais), dans la vue web du système :
  WebKitGTK sous Linux, WebView2 sous Windows. Rust + Tauri 2 (`desktop/`).
- Même pont natif que le Mac (`platform/desktop.ts`) : l'interface ne voit qu'un appareil de bureau
  (`desktop` dans l'interface, `mac` restant pour ce qui est propre au Mac : icône de la barre des menus).
- Stockage : un fichier chiffré (XChaCha20-Poly1305) dont la clé est dans le trousseau du système
  (Gestionnaire d'identification sous Windows, Secret Service sous Linux, à défaut un fichier
  réservé à l'utilisateur) : le Gestionnaire d'identification de Windows limite un secret à 2,5 Ko.
- Presse-papier : `clipboard-rs` (évènements de changement sous Windows et X11 ; Wayland via XWayland),
  marquage « secret » de ce qu'on écrit et respect de celui des gestionnaires de mots de passe.
- Icône dans la zone de notification (clic : fenêtre ; menu : Ouvrir, Pause, Recharger, Quitter) ;
  fermer la fenêtre garde l'appli active ; une seule instance, relancer ramène la fenêtre.
- Glisser-déposer dans la fenêtre (pas sur l'icône : Windows et Linux ne le permettent pas).
- Compilées dans Docker (`desktop/build.sh`) : Linux natif, Windows croisé avec cargo-xwin et NSIS.
  Compilées et non testées sur une vraie machine au 2026-11-11.

## 9. Relais

- Un conteneur `node:lts-alpine` : Node (HTTP + WebSocket, fichiers statiques) et Redis
  lancé comme processus enfant (configuration par l'entrée standard, mot de passe aléatoire).
- Redis : `maxmemory` = 80 % de la limite mémoire du conteneur, `noeviction` (le relais
  refuse les envois quand il est plein plutôt que d'être tué) ; aucune écriture disque
  sauf `PERSIST=true` (instantanés RDB + sauvegarde à l'arrêt, volume `/data`).
- Variables : `MAX_STORAGE` (0 = illimité), `MAX_TTL` (7 j), `PERSIST` (false) ; `mem_limit: 4g`.
- Conteneur en lecture seule, `cap_drop: ALL`, `no-new-privileges`, `pids_limit`, utilisateur non root.
- Protocole : requêtes JSON `{ rid, op, … }`, réponses `{ rid, ok, … }`, évènements `{ ev, … }` ;
  morceaux en trames binaires. Limites : 200 requêtes/s par connexion, 32 connexions par IP.
- Ne journalise jamais de contenu ni d'identifiant de salle.
- Déploiement : derrière un reverse proxy TLS, voir `docs/deploiement.md`.

## 10. Limites connues

- Le code de la PWA est servi par le relais : un relais compromis pourrait servir un code
  malveillant aux téléphones. L'appli Mac embarque son interface.
- Appli Mac signée ad hoc, non notariée : « Ouvrir quand même » au premier lancement,
  et accès au Trousseau redemandé après chaque recompilation.
- Un envoi interrompu reprend tant que l'appli reste ouverte, pas après son redémarrage.
- Un appareil qui ne s'est pas connecté depuis une rotation des clés doit être réappairé.

## 11. Pistes à l'étude

- **Notifications push** sur mobile, avec les applis natives : le relais enverrait un signal
  vide (sans contenu) via Google ou Apple, qui verraient l'heure des envois mais jamais
  le contenu. Option désactivée par défaut.
- Appli iOS native (Capacitor), sur le modèle de l'appli Android.
- Transport natif pour le mode local entre applis natives (TCP/QUIC + découverte Bonjour/mDNS,
  à la LocalSend) : débit proche du Wi-Fi, mais seulement entre applis natives ; WebRTC reste
  le seul moyen pour l'appli web.
- Relais auto-hébergé à la maison : réglage « Serveur » dans les applis (aujourd'hui `defaults
  write` sur Mac, adresse figée dans l'APK ; un appareil qui rejoint prend le serveur du lien).
- Reprise des envois après redémarrage de l'appli (aujourd'hui, la reprise suppose que
  l'appli soit restée ouverte : le fichier n'est gardé qu'en mémoire).
