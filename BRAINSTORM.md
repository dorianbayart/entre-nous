# Entre Nous — conception

Presse-papier et fichiers partagés entre les appareils d'une même personne (Mac, Android,
Linux, Windows, iPhone, navigateur), chiffrés de bout en bout, sans ouvrir de port sur la box.
Ce document garde les choix structurants et ce qui est réellement implémenté ;
`README.md` donne les commandes.

## 1. Principes

- Bidirectionnel, entre **appareils égaux** d'un même groupe (Mac ↔ téléphone, téléphone ↔ téléphone).
- Mac : appli de barre des menus, toujours active.
- Téléphone : PWA, connectée **uniquement au premier plan** (batterie, vie privée).
- Appairage (et installation de la PWA) par QR code. Plusieurs groupes indépendants.
- Fonctionne partout sans configuration réseau : tout passe par un relais en HTTPS.
- Le relais ne peut rien lire et ne garde rien sur disque.

## 2. Décisions structurantes

| Sujet | Décision |
|---|---|
| Architecture | Cœur TypeScript commun ; PWA (Android, iOS, navigateurs) ; Mac = Swift + WKWebView ; Linux et Windows = Tauri (§8 ter) ; Android = Capacitor ; les applis embarquent la même interface |
| Interface | Alpine.js en build CSP (pas d'`eval`), politique de sécurité stricte |
| Langues | Français et anglais (interface, page d'accueil, docs) ; langue du système ou du navigateur, l'anglais pour toute autre ; réglage par appareil (Réglages → Langue) ; page d'accueil négociée par `Accept-Language` sur `/`, `/fr/` et `/en/` explicites |
| Transport | Relais WebSocket ; WebRTC direct entre appareils du même réseau (mode local, §8 bis) |
| Hors ligne | Boîte aux lettres chiffrée sur le relais, historique partagé jusqu'à expiration |
| Rétention | Réglage du groupe, modifiable par tout membre, 24 h par défaut, plafonnée par `MAX_TTL` (7 j) ; raccourcir s'applique aussi aux éléments existants, allonger seulement aux nouveaux |
| Retrait d'un appareil | Par n'importe quel membre ; rotation des clés, l'historique suit les membres restants |
| Taille des envois | Pas de limite pour un envoi manuel ; partage automatique du Mac limité par un réglage du groupe (1 Mo par défaut, 10 Mo, 100 Mo) ; le relais est borné par `MAX_STORAGE` et `mem_limit` |
| Taille de l'historique | Réglage du groupe : 1, 10 (défaut) ou illimité ; appliquée par les appareils, qui suppriment les plus anciens non épinglés (le relais ne sait pas lesquels sont épinglés ; la note en direct ne compte pas) |
| Relais | Un conteneur Node + Redis en RAM, sans volume par défaut ; volume optionnel (`PERSIST`) |
| Adresses | Page d'accueil sur `/`, PWA sous `/app/`, appli Mac en `/download/Entre-Nous-mac.zip` ; relais public `https://entrenous.0xdba.dev` |

## 3. Cryptographie

| Brique | Choix (bibliothèques `@noble`) |
|---|---|
| Échange de clés | X25519 + ML-KEM-768 hybride (combinateur X-Wing) |
| Signatures | Ed25519 |
| Chiffrement | XChaCha20-Poly1305 |
| Dérivation | HKDF-SHA-256, étiquettes `entrenous/v1/<usage>` |

- **Pré-clés** : chaque appareil publie pour chaque groupe une pré-clé X-Wing signée,
  renouvelée chaque jour. Une ancienne pré-clé est détruite après son remplacement
  + la rétention du groupe (+1 h) : la confidentialité persistante suit la rétention.
- **Éléments** : une clé aléatoire chiffre le contenu une seule fois ; elle est enveloppée
  (construction type HPKE) pour la pré-clé de chaque membre. Les métadonnées sont signées
  par l'expéditeur.
- **En-tête chiffré** (type, nom, taille, miniature, texte court) bourré à un multiple de 256 o ;
  texte de moins de 64 Ko dans l'en-tête, au-delà envoyé comme fichier.
- **Contenus** découpés en morceaux de 1 Mio ; chaque morceau est authentifié avec son
  index, l'identifiant de l'élément et un drapeau « dernier » (ni réordonnable ni tronquable) ;
  le dernier morceau est bourré à un multiple de 64 Kio.
- **Mac** : ce qu'il écrit dans le presse-papier est marqué `org.nspasteboard.ConcealedType` ;
  il ignore ce que les gestionnaires de mots de passe marquent Concealed/Transient/AutoGenerated.

## 4. Groupes, appairage, retrait

- **Groupe** : secret de 256 bits partagé par les membres. Salle sur le relais =
  `sha256(kdf(secret, "room"))` : le relais ne voit qu'un identifiant opaque.
- **État du groupe** (membres, nom, rétention) : signé, chiffré avec `kdf(secret, "state")`,
  versionné sur le relais (compare-and-swap). Fusion : union des membres, retraits
  définitifs, nom et rétention les plus récents. Un membre ajouté pendant qu'un appareil
  était hors ligne est accepté s'il a été ajouté par un membre connu (chaîne de parrainage).
- **Appairage** : le QR contient `https://…/app/#p=<secret à usage unique>`. Le fragment
  n'est jamais envoyé au serveur et la page l'efface aussitôt. Les deux appareils se
  retrouvent sur un canal du relais dérivé du secret, et l'invitant envoie l'état du groupe
  chiffré avec une clé dérivée du même secret. Invitation valable 3 min, pour un seul appareil.
  N'importe quel membre peut inviter.
- **iOS** : une PWA installée ne partage pas le stockage de Safari ; l'appli invite donc
  à l'installer d'abord, puis à scanner depuis l'appli (scanner intégré, `jsQR`).
- **Retrait** : nouveau secret de groupe transmis par un élément « rotation » enveloppé
  pour les seuls membres restants ; l'historique est d'abord déplacé dans la nouvelle salle
  (`items.move`, pré-clés conservées pour qu'il reste lisible), puis l'ancienne salle ne garde
  que la rotation (`room.purge`). L'appareil retiré, s'il se reconnecte, s'efface lui-même.
  Un groupe réduit à un membre est dissous (`room.delete`, marqueur « dissous » 30 j).
- Les appairages vivent sur les appareils : un relais vidé ne casse aucun groupe,
  les appareils republient état et pré-clés à la connexion.

## 5. Historique et boîte aux lettres

- Un envoi = un **élément** sur le relais : métadonnées signées, en-tête chiffré,
  enveloppes, morceaux. Les membres connectés le reçoivent aussitôt, les autres à
  l'ouverture de l'appli.
- Tout l'historique reste disponible jusqu'à expiration : chaque élément peut être recopié,
  enregistré ou supprimé par n'importe quel membre.
- Les appareils ne téléchargent un contenu qu'au moment de le copier ou de l'enregistrer.
- Un élément expiré quitte l'historique local à la seconde.
- **Partage automatique du Mac** (et Linux, Windows) : chaque copie est envoyée tout de suite
  au relais, qu'un autre appareil soit connecté ou non (décision du 2026-11-25 ; avant, la copie
  attendait qu'un appareil se connecte). La limite d'historique du groupe s'applique : les plus
  anciens éléments laissent la place. La **Pause** arrête l'envoi automatique.
  Une copie plus grosse que la limite du groupe n'est ni lue ni envoyée : un message invite
  à passer par « Fichier ». Les envois manuels passent toujours par la boîte aux lettres.
- **À la connexion** (ouverture de l'appli, sortie de veille), le dernier élément reçu
  pendant l'absence est mis dans le presse-papier s'il a moins d'une minute (Mac, Android).
- **Suppression** : un élément (confirmation selon le réglage de l'appareil, activée par défaut),
  ou « Tout supprimer » (historique et note, pour tous les membres, toujours confirmé).
- **Réception** : le Mac et Android (au premier plan) écrivent l'élément reçu dans le
  presse-papier ; iOS exige un toucher (« Copier ») et ne permet pas l'effacement automatique.
- Tout envoi attend que la connexion soit établie et les pré-clés des membres chargées
  (sinon un partage Android, reçu pendant la connexion, n'était lisible que par l'expéditeur).
- **Accusés de réception** : double coche en haut à droite de chaque élément, envoyé ou reçu,
  comme dans une messagerie ; tous les appareils montrent les mêmes coches. 1re coche : un appareil l'a reçu, colorée quand un
  appareil l'a lu ; 2e coche : tous l'ont reçu, colorée quand tous l'ont lu. Rien avant la
  première réception. Toucher les coches donne le détail par appareil (heure de réception, de
  lecture). « Reçu » = élément arrivé entier ; « lu » = ouvert, copié ou enregistré par la
  personne (pas la copie automatique) ; « tous » = appareils pour lesquels l'élément a été
  chiffré, sauf l'expéditeur, encore dans le groupe. Un élément reçu dont on est le seul
  destinataire (groupe de deux) n'en a pas : elles ne diraient que ce qu'on a fait. L'accusé est chiffré avec la clé de l'élément et gardé par le
  relais avec l'élément (champ `a:{appareil}`) : l'expéditeur hors ligne le retrouve plus tard.
- **Épingles** : la punaise garde un élément en haut de l'historique (puis des résultats de
  recherche), sur tous les appareils ; épinglés triés par date entre eux. Il expire comme les
  autres, mais la taille de l'historique ne le compte pas et ne le supprime pas. État chiffré avec
  la clé de l'élément, de taille fixe, épinglé ou non (champ `pin` de l'élément, `{p, at}`, le
  plus récent l'emporte) : le relais ne sait pas lesquels sont épinglés. Comme il ne peut donc
  plus appliquer la taille de l'historique, ce sont les appareils en ligne qui suppriment les
  éléments en trop (le relais ne coupe plus de lui-même). Désépingler un élément trop ancien le
  supprime : l'appli le demande d'abord. Le « dernier élément » (copie automatique, `get` du CLI)
  suit la date, pas la position à l'écran.
- **Liens et QR codes des textes** : un texte qui contient un lien (`core/search.ts`, `linkOf` :
  le premier, sans la ponctuation qui le suit) a un bouton « Ouvrir » (avant « Copier » s'il n'est
  qu'un lien), qui passe par la plateforme (`openUrl` : nouvel onglet, `NSWorkspace`, plugin opener
  de Tauri, `Intent.ACTION_VIEW` ; `http` et `https` seulement). Un texte de 1 000 octets au plus, ou
  un fichier texte (`.txt`, `.md`…) de cette taille, s'affiche en QR code (UTF-8), fait sur
  l'appareil : rien ne passe par le relais, à la différence d'un lien de partage.
- **Recherche** : sur l'appareil seulement (`core/search.ts`, partagé avec le CLI), dans ce que
  l'en-tête donne déjà : texte, nom de fichier, extrait d'un fichier texte, appareil. Sans accents,
  majuscules, tirets ni apostrophes ; tous les mots doivent y être. Loupe dans la barre du haut
  (⌘F / Ctrl+F), qui devient le champ ; puces par type (textes, liens, images, vidéos, audio,
  documents, dossiers), seulement celles présentes. Mots surlignés ; un long texte s'affiche à
  partir du mot trouvé. Ordinateur : ↑↓ choisit, Entrée copie, Échap efface puis ferme. Pas
  cherché : les fichiers d'un dossier (index dans l'archive), le texte des images. Rien n'est
  gardé des recherches.

## 6. Note en direct

- Un champ texte par groupe, synchronisé à chaque frappe. C'est un élément `note` sans
  contenu : sa clé est enveloppée pour chaque membre, et chaque modification rechiffre
  tout le texte (bourré à 256 o). Le relais n'en garde que la dernière version (`note.put`),
  et la rétention repart de la dernière modification.
- Un texte vide supprime la note du relais. Un appareil arrivé après coup la reçoit quand
  son auteur la renvoie (nouvelle clé). En cas de frappe simultanée, la dernière version gagne ;
  une modification reçue pendant qu'on tape attend une pause de 1,5 s.

## 7. Contenus et plateformes

| | Envoyer | Recevoir |
|---|---|---|
| Mac, Linux, Windows | surveillance du presse-papier (texte, image, fichier copié dans le gestionnaire de fichiers), glisser-déposer | texte et image dans le presse-papier ; autre fichier écrit dans le dossier temporaire puis mis dans le presse-papier |
| Android | « Envoyer le presse-papier », « Fichier », « Partager → Entre Nous » (Web Share Target) | presse-papier si l'appli a le focus ; fichiers via la feuille de partage |
| iOS | « Envoyer le presse-papier » (bulle « Coller »), « Fichier » | toucher « Copier » ; fichiers via la feuille de partage |
| Navigateur | Ctrl+V, glisser-déposer, « Fichier » | « Copier », téléchargement |

- Mac : fichiers reçus effacés à l'expiration de l'élément ; « Enregistrer sous… » pour les garder.
- Mac : bouton **Pause** (et entrée du menu de l'icône) : le presse-papier n'est plus lu,
  les copies faites pendant la pause ne partent jamais ; l'icône passe en ⏸.
- Mac : `beginActivity` contre App Nap ; menu Édition invisible pour Cmd+A/C/V/X/Z ;
  sélecteur de fichiers natif pour le bouton « Fichier ».
- Mac : glisser un fichier (plusieurs, une image, un texte) sur l'icône de la barre des menus
  l'envoie aussitôt, sans limite de taille ni pause, et ouvre la fenêtre sur sa progression.
- Mac : notification à la réception quand la fenêtre est fermée (réglage, activé par défaut) ;
  elle n'indique que le type et l'expéditeur, jamais le contenu.
- Connexion : test de vie toutes les 20 s quand elle est silencieuse ; vérification immédiate
  à la sortie de veille du Mac et au retour du réseau.
- Espace restant sur le relais affiché dans les réglages, alerte sous 10 %.
- Envoi d'un fichier : il apparaît sur tous les appareils dès le début, avec sa progression
  (évènement `progress` du relais à chaque bloc reçu) ; « Copier » et « Enregistrer » attendent
  la fin, et la réception automatique (Mac, notification, boîte aux lettres) ne part qu'à ce
  moment-là. Sans nouveau bloc depuis 30 s : « envoi en pause ».
- **Aperçus** (photo, vidéo, audio, PDF, texte, Markdown), dans l'appli, sans enregistrer :
  - faits par l'**émetteur** pour ce qui s'affiche avant tout téléchargement, joints à l'en-tête
    chiffré : aperçu de 720 px au plus de côté, JPEG progressif qualité 85 (encodeur maison,
    `ui/jpeg.ts` : le canvas ne fait que du JPEG séquentiel), 30 à 100 Ko pour une photo, qualité
    70, 55 puis 40 au-delà de 160 Ko ; la miniature de l'historique **et** l'image de la
    visionneuse : l'original ne se télécharge que pour être copié ou enregistré (une image sans
    aperçu : un message ; en mode local, l'original). SVG dessiné à 720 px, dans un `<img>` (pas de
    script) ; PDF : première page à 384 px ; dimensions ; vidéo : image à 1 s (ou au dixième) et durée ; audio : durée ; PDF : première page et
    nombre de pages ; texte : 280 premiers
    caractères. L'émetteur est aussi celui qui sait décoder ses fichiers (HEIC d'un iPhone).
    Rien en mode local (l'aperçu est du contenu) ;
  - le **récepteur** lit le contenu à l'ouverture, à la demande : `engine.reader()` déchiffre les
    blocs demandés (relais ou liaison directe, même pendant l'envoi), en garde 16, prend les suivants
    d'avance, et garde la connexion ouverte en arrière-plan tant qu'il est ouvert ;
  - **vidéo en continu** : MediaSource (ManagedMediaSource sur iPhone, iOS 17.1+) et mp4box.js
    (BSD-3), qui lit l'index d'un MP4/MOV où qu'il soit et le découpe en fragments ; ~30 s
    d'avance en mémoire. Ailleurs (WebM, iOS plus ancien) : téléchargement entier puis lecture ;
  - **audio en continu** : M4A par le même chemin (mp4box, piste son seule) ; MP3 donné tel quel à
    MediaSource (`audio/mpeg`, horodaté par le navigateur), un saut part de la trame trouvée à la
    place du moment (table des matières Xing/Info, sinon débit) ; Opus (Ogg) remballé à la volée
    en MP4 fragmenté (`audio/mp4; codecs="opus"`), horodaté par la position de chaque page, un saut
    recule jusqu'à une page qui n'est pas plus tard ; FLAC : ses trames telles quelles en MP4
    fragmenté (`audio/mp4; codecs="flac"`), chacune bornée par son CRC-16 et horodatée par son
    numéro, saut par la table de saut ou par recherche ; WAV (entiers 8, 16, 24 bits) : son PCM mis
    en trames FLAC « verbatim » (rien à compresser), même chemin, saut exact. Ogg Vorbis, WAV en
    flottants : téléchargés entiers puis lus ;
  - **incrustation** : API standard (navigateurs, Mac avec la préférence
    `allowsPictureInPictureMediaPlayback` du WKWebView, qui continue popover fermé) ; Android :
    PiP natif de l'activité (bouton lecture/pause, entrée automatique en quittant l'appli) ;
    Linux, Windows (aucune API dans WebKitGTK, WebView2 non testé) : la fenêtre se réduit à la
    vidéo, au premier plan ;
  - **PDF** : pdf.js (Apache-2.0, build « legacy »), branché sur `engine.reader()` par
    `PDFDataRangeTransport` : il ne demande que les plages utiles (table, puis objets des pages
    affichées), par 128 Ko. Pages dessinées dans un canvas à l'approche de l'écran
    (IntersectionObserver), oubliées loin de lui ; zoom 100 à 300 %. Par-dessus : la couche de
    texte de pdf.js (`TextLayer`, sélection, « Copier la sélection » pour le Mac sans menu Édition)
    et les liens (`getAnnotations`) : http(s)/mailto en `_blank`, internes vers leur page. Worker servi par l'appli
    (`app/pdf.worker.js`), sans scripts PDF, sans XFA, sans WebAssembly (interdit par la CSP : pas
    de JPEG 2000), sans fetch depuis le worker ;
  - Markdown : markdown-it (MIT) sans HTML, images non chargées, liens http(s)/mailto seuls.
    mp4box, pdf.js et markdown-it ne se chargent qu'à l'ouverture (ou à l'envoi, pour pdf.js) d'une
    vidéo, d'un M4A, d'un PDF ou d'un Markdown.
- Pendant un transfert : écran maintenu allumé (Wake Lock dans l'appli web, `FLAG_KEEP_SCREEN_ON`
  sur Android), mise en veille du Mac bloquée ; l'appli passée en arrière-plan ne se déconnecte
  qu'une fois le transfert fini.
- Coupure (réseau, veille) pendant un transfert : il attend le retour de la connexion puis
  reprend avec les blocs qui manquent (`chunk.have`), jusqu'à l'expiration de l'élément.

## 8. Appli Android (Capacitor)

- Même interface web, embarquée dans l'APK (comme sur Mac : le code ne vient pas du relais).
- Plugin natif `EntreNousPlugin.java` :
  - stockage chiffré par une clé AES-GCM du Keystore Android (jamais extractible),
    sauvegarde cloud et transfert entre appareils désactivés ;
  - presse-papier sans toucher, marqué sensible (pas d'aperçu) ; images via le FileProvider ;
  - « Partager → Entre Nous » (texte, fichiers), fichiers reçus proposés par la feuille de partage ;
  - liens d'invitation (App Links vérifiés par `assetlinks.json`), bouton retour,
    passage premier plan / arrière-plan (connexion seulement au premier plan).
- Compilée dans Docker (`android/build.sh`), signée par une clé gardée hors du repo,
  APK proposé sur la page d'accueil.

## 8 bis. Mode local (transferts directs)

- Deux appareils du même réseau se relient en WebRTC (canal de données) **sans STUN ni TURN** :
  seuls les candidats « hôte » existent, la liaison ne se fait donc qu'en local, jamais par un tiers.
- Mise en relation par le relais (`signal`, transmis sans être stocké), messages chiffrés avec
  une clé dérivée du secret du groupe et liés aux deux appareils (AAD `de>à`).
- Ce qui passe sur la liaison : les mêmes blocs scellés que sur le relais, servis par l'appareil
  qui a envoyé l'élément (il garde le contenu en mémoire tant qu'il est ouvert, `outbox`).
- **Automatique** (par défaut) : l'envoi part aussi sur le relais (appareils absents ou ailleurs) ;
  un appareil du même réseau télécharge en direct, même avant la fin de l'envoi. Échec de la
  liaison (autre réseau, réseau qui isole les appareils) : le relais prend le relais, sans message.
  La liaison est préparée dès qu'un élément arrive, pour ne pas attendre au clic.
- **Réseau local uniquement** (réglage du groupe) : seule l'annonce chiffrée passe par le relais,
  sans contenu ni miniature, textes compris ; le relais n'en reçoit aucun bloc. Un élément n'est
  disponible que tant que son expéditeur est ouvert sur le même réseau.
- Le transport est injecté dans le moteur (`peers.ts` + `webrtc.ts`) : les tests le remplacent
  par une liaison en mémoire (`test/local.test.ts`).
- Débit (mesuré le 2026-11-10) : une connexion WebRTC plafonne vers 16–18 Mo/s entre deux
  navigateurs, deux en parallèle montent à 31 Mo/s (trois n'apportent rien) : deux liaisons par
  appareil, les blocs vont à la moins chargée. Contrôle de flux par l'évènement
  `bufferedamountlow` (pas de minuterie, ralentie quand la page est cachée), messages de 256 Ko,
  blocs préparés en parallèle. Résultats : 22–26 Mo/s entre deux Chrome du Mac, 9,8 Mo/s du
  Pixel 6a à l'appli Mac en Wi-Fi ; par le serveur, l'envoi est limité par le débit montant de
  la connexion internet (quelques centaines de Ko/s sur une box ADSL ou VDSL).
- Vitesse affichée sur chaque transfert (serveur ou direct, envoi ou réception) et sur un
  élément en cours d'envoi ; l'expéditeur voit « ↑ … · en direct vers <appareil> ».

## 8 ter. Applis Linux et Windows (Tauri)

- Même interface web, embarquée (le code ne vient pas du relais), dans la vue web du système :
  WebKitGTK sous Linux, WebView2 sous Windows. Rust + Tauri 2 (`desktop/`).
- Même pont natif que le Mac (`platform/desktop.ts`) : l'interface ne voit qu'un appareil de bureau
  (`desktop` dans l'interface, `mac` restant pour ce qui est propre au Mac : icône de la barre des menus).
- Stockage : un fichier chiffré (XChaCha20-Poly1305) dont la clé est dans le trousseau du système
  (Gestionnaire d'identification sous Windows, Secret Service sous Linux, à défaut un fichier
  réservé à l'utilisateur) : le Gestionnaire d'identification de Windows limite un secret à 2,5 Ko.
- Presse-papier : `clipboard-rs` (évènements de changement sous Windows et X11 ; Wayland via XWayland),
  marquage « secret » de ce qu'on écrit et respect de celui des gestionnaires de mots de passe.
- Icône dans la zone de notification (clic : fenêtre ; menu : Ouvrir, Pause, Recharger, Quitter) ;
  fermer la fenêtre garde l'appli active ; une seule instance, relancer ramène la fenêtre.
- Glisser-déposer dans la fenêtre (pas sur l'icône : Windows et Linux ne le permettent pas).
- Compilées dans Docker (`desktop/build.sh`) : Linux natif, Windows croisé avec cargo-xwin et NSIS.
  Compilées et non testées sur une vraie machine au 2026-11-11.

## 8 quater. Serveur de son choix

- Applis natives : **Réglages → Serveur → Adresse du serveur** (préférence de l'appareil). Vérifié
  par une connexion WebSocket (pas de CORS, contrairement à `fetch` depuis les applis), puis serveur
  des nouveaux groupes ; un groupe où l'appareil est seul est recréé dessus (l'ancien est dissous) ;
  un groupe partagé reste sur son serveur (le lien d'invitation porte le serveur du groupe).
- Appli web : toujours le relais qui la sert (sa CSP n'autorise pas d'autre serveur).

## 8 quinquies. Ligne de commande (`cli/`)

- **Pourquoi** : envoyer un fichier depuis un serveur ou une CI, récupérer une photo dans un script,
  et donner aux agents d'IA (Claude Code et les autres, qui ont un shell) un moyen de remettre ce
  qu'ils produisent ou de poser une question, sans configuration.
- **Un appareil de plus** (plateforme `cli`, « Terminal »), sur le même cœur : rien de nouveau dans
  le protocole ni dans la cryptographie. Un seul fichier (`dist/entrenous.mjs`, esbuild), sans
  dépendance, Node 22 (WebSocket, `fs.openAsBlob`).
- **CLI plutôt que serveur MCP** : un MCP local s'installe et se lance comme un CLI, avec en plus une
  déclaration dans la configuration du client ; un MCP distant (hébergé par le relais) devrait
  chiffrer et déchiffrer pour l'agent, donc voir le contenu : exclu. Un MCP pourra venir plus tard
  comme surcouche du CLI, pour les clients sans shell.
- **Association** : une invitation, comme pour tout appareil ; c'est l'étape humaine voulue (le
  consentement). `invite` attend en premier plan : l'invitation n'existe que tant que son auteur
  écoute le canal d'appairage.
- **Clés dans des fichiers en clair** (`0600`, dossier `0700`), comme des clés SSH : le trousseau
  du système n'est pas joignable partout où tourne un CLI (serveurs, conteneurs, CI). Aucun contenu
  sur le disque, sauf les fichiers enregistrés à la demande.
- **Plusieurs processus, une identité** : écritures sous verrou (un dossier `.lock`), liste des
  groupes déduite des fichiers présents, et fusion des prékeys à l'écriture d'un groupe : une
  prékey créée par un autre processus n'est jamais perdue.
- **Relais seulement** : pas de WebRTC dans Node ; un groupe « Réseau local uniquement » est refusé.
- **Sorties pour les scripts** : résultats sur stdout, messages sur stderr, `--json`, codes de sortie
  stables (`124` pour un délai dépassé), rien d'interactif hors terminal (`--yes`).
- **Sécurité des fichiers reçus** : le nom donné par l'expéditeur est réduit à son dernier élément,
  sans point initial ; jamais de remplacement sans `--force`.
- **Diffusion** : `entrenous-cli.tgz` dans chaque release, installable par `npm install -g <url>`.
  Pas de publication sur le registre npm : double authentification matérielle obligatoire et jetons
  à renouveler, trop lourd pour ce que ça apporte.

## 8 sexies. Liens de partage

- **Pourquoi** : donner un élément à quelqu'un hors du groupe (un ami, un collègue), sans l'inviter
  dans le groupe (il verrait tout l'historique) ni passer par un autre service.
- **Lien vers un élément de l'historique** (pas d'envoi à part) : rien n'est renvoyé, c'est
  instantané même pour un gros fichier. Bouton discret (icône de partage, info-bulle « Partager ») ;
  la vue glisse vers une page proche de l'invitation : QR code, lien, durée.
- **Créé tout de suite, valable 1 h** ; durées 10 min, 1 h, 24 h, 7 j (bornées par `MAX_TTL`), comptées
  à partir du choix ; changer la durée garde la même adresse. Pas d'option « une seule ouverture » :
  10 min ou 1 h en tiennent lieu. Pas de signalement de lien, pas de nouveau réglage du serveur.
- **Indépendant de l'élément** : un élément qui expire ou est supprimé du groupe garde ses blocs pour
  ses liens (`r:{salle}:sh:{id}`, durée des blocs = la plus tardive), et ses liens le suivent quand
  l'historique change de salle (`items.move`), ou restent dans l'ancienne après une dissolution.
- **Seulement sur l'appareil qui l'a créé** : une entrée de son historique (encadrée de pointillés),
  qui disparaît à l'expiration. Lui seul peut changer la durée ou supprimer le lien (second secret,
  empreinte sur le relais) ; re-partager un élément crée un nouveau lien.
- **Cryptographie** : `https://<relais>/s/#<secret>` ; le relais voit `sha256(kdf(secret, "share/id"))`
  et la clé de l'élément scellée avec `kdf(secret, "share/key")` ; l'en-tête et les blocs sont ceux de
  l'élément, inchangés.
- **Page `/s/`** (`src/share/`, servie par le relais seulement) : DOM simple, sans Alpine ; texte à
  copier, aperçu d'une image ou d'un PDF (fait par l'émetteur), vidéo et audio en continu (même lecteur
  que l'appli), début d'un fichier texte, téléchargement.

## 8 septies. Dossiers

- **Un dossier = un élément** (`kind: 'folder'`) : une seule carte dans l'historique, une seule durée
  de vie, une seule suppression. Aucun changement du relais ni du protocole.
- **Une seule archive chiffrée**, découpée en blocs de 1 Mo comme un fichier (`src/core/folder.ts`) :
  `"ENF1"`, longueur du sommaire, sommaire (JSON : chemins, tailles, positions, aperçus), aperçus,
  fichiers bout à bout. Le sommaire et les aperçus viennent d'abord : l'autre appareil parcourt le
  dossier dès les premiers Mo, même pendant l'envoi. Un fichier du dossier n'est qu'une plage du
  contenu : aperçus, lecture en continu et téléchargement partiel passent par le `ChunkReader`.
- **L'en-tête** ne garde qu'un résumé (`folder: { files, dirs, bytes }`) et la vignette de la carte :
  les 4 premiers aperçus en mosaïque (un seul s'il y en a moins de 4), sinon l'icône de dossier.
- **Aperçus faits par l'émetteur**, comme pour un fichier seul : JPEG progressif de 720 px au plus,
  qualité 85, pour chaque image, vidéo et PDF ; début des fichiers texte. Ils sont dans l'archive (pas
  dans l'en-tête, limité par `META_MAX`) et lus seulement pour les lignes à l'écran.
- **Fichiers système laissés de côté** (.DS_Store, Thumbs.db, desktop.ini, `._*`) ; les autres
  fichiers cachés partent. Les dossiers vides sont gardés. Les chemins reçus sont vérifiés (`safePath` :
  ni `..`, ni chemin absolu) avant tout affichage ou écriture.
- **Envoi** : bouton **Dossier** sur ordinateur, menu **Fichier → Un dossier…** sur téléphone (appli
  Android seulement : ni Safari sur iPhone ni le navigateur d'Android ne choisissent un dossier),
  glisser-déposer (`webkitGetAsEntry`). Au-delà de 10 fichiers ou 40 Mo, un résumé à confirmer (avec
  la place libre du serveur). Un dossier copié dans le gestionnaire de fichiers part seul sous ces
  mêmes seuils ; au-delà, une notification et le même résumé.
- **Réception** : navigateur plein écran, un niveau à la fois, fil d'Ariane ; grille (avec « Choisir »)
  quand le dossier affiché n'a que des images et des vidéos, liste à cases sinon. L'aperçu habituel
  passe d'un fichier au suivant du même dossier ; pas de suppression depuis l'intérieur.
- **Enregistrement** : un fichier seul comme d'habitude ; plusieurs, le dossier recréé là où l'appareil
  sait l'écrire (applis : sélecteur natif ; Chrome et Edge : `showDirectoryPicker`), sinon un ZIP sans
  compression fabriqué au fil de la lecture (`src/core/zip.ts`, ZIP64 au-delà de 4 Go). Le CLI recrée
  le dossier, ou écrit un ZIP sur la sortie standard.
- **Lien de partage d'un dossier** : la page `/s/` montre le même navigateur (`ui/folder-view.ts`, en
  DOM simple, commun aux deux).
- **Plus tard** : recherche par nom dans un dossier, avec la recherche dans l'historique.

## 8 octies. Demandes de fichiers

- **Pourquoi** : le sens inverse des liens de partage. Récupérer les photos des autres après un
  évènement, ou les fichiers d'un collègue, sans l'inviter dans le groupe.
- **Entrée** : icône « Recevoir des fichiers » dans la barre du haut ; la vue glisse vers une page
  proche du lien de partage : message facultatif (affiché sur la page), QR code, lien, durée.
  **Créée tout de suite, valable 24 h** ; 1 h, 24 h, 7 j. **Aucune limite de taille** propre à la
  demande : seule la place du serveur compte.
- **Connue de tout le groupe** : la demande est dans l'état du groupe (`drops`), avec son secret et
  la graine de sa paire de clés ; tous les appareils l'affichent en tête de l'historique (pointillés),
  la changent ou la suppriment. Une demande finie reste 8 jours dans l'état, pour ouvrir ce qui est
  arrivé par elle.
- **Page `/r/`** (`src/drop/`, servie par le relais seulement) : liste des fichiers qui avance,
  prénom facultatif (gardé dans le navigateur) ; chaque choix part tout de suite, pas de page de fin.
- **Un envoi = un élément** : un fichier seul reste un élément simple, plusieurs fichiers choisis
  d'un coup forment un dossier (« Envoi de Marie »), qui ne compte qu'une fois dans l'historique.
  Aperçus faits par la page, comme par l'émetteur dans l'appli.
- **Cryptographie** : `https://<relais>/r/#<secret>` ; le relais voit `sha256(kdf(secret, "drop/id"))`
  et `{ clé publique, message }` scellés avec `kdf(secret, "drop/info")`. Chaque élément est scellé
  comme un élément du groupe, sa clé enveloppée pour la clé publique de la demande (X-Wing), sans
  signature (`from` = l'identifiant de la demande). Le lien permet d'envoyer, jamais de lire.
- **Relais** : `d:{demande}` (salle, durée et taille d'historique du groupe), qui suit le groupe lors
  d'un retrait d'appareil ; un envoi commencé peut finir jusqu'à 24 h après la fin de la demande.
  Pas en « Réseau local uniquement ».

## 9. Relais

- Un conteneur `node:lts-alpine` : Node (HTTP + WebSocket, fichiers statiques) et Redis
  lancé comme processus enfant (configuration par l'entrée standard, mot de passe aléatoire).
- Redis : `maxmemory` = 80 % de la limite mémoire du conteneur, `noeviction` (le relais
  refuse les envois quand il est plein plutôt que d'être tué) ; aucune écriture disque
  sauf `PERSIST=true` (instantanés RDB + sauvegarde à l'arrêt, volume `/data`).
- Variables : `MAX_STORAGE` (0 = illimité), `MAX_TTL` (7 j), `PERSIST` (false) ; `mem_limit: 4g`.
- Conteneur en lecture seule, `cap_drop: ALL`, `no-new-privileges`, `pids_limit`, utilisateur non root.
- Protocole : requêtes JSON `{ rid, op, … }`, réponses `{ rid, ok, … }`, évènements `{ ev, … }` ;
  morceaux en trames binaires. Limites : 200 requêtes/s par connexion, 32 connexions par IP.
- Ne journalise jamais de contenu ni d'identifiant de salle.
- Déploiement : derrière un reverse proxy TLS, voir `docs/deploiement.md`.

## 10. Limites connues

- Le code de la PWA est servi par le relais : un relais compromis pourrait servir un code
  malveillant aux téléphones. L'appli Mac embarque son interface.
- Appli Mac signée ad hoc, non notariée : « Ouvrir quand même » au premier lancement,
  et accès au Trousseau redemandé après chaque recompilation.
- Un envoi interrompu reprend tant que l'appli reste ouverte, pas après son redémarrage.
- Un appareil qui ne s'est pas connecté depuis une rotation des clés doit être réappairé.

## 11. Pistes à l'étude

- **Notifications push** sur mobile, avec les applis natives : le relais enverrait un signal
  vide (sans contenu) via Google ou Apple, qui verraient l'heure des envois mais jamais
  le contenu. Option désactivée par défaut.
- Appli iOS native (Capacitor), sur le modèle de l'appli Android.
- Transport natif pour le mode local entre applis natives (TCP/QUIC + découverte Bonjour/mDNS,
  à la LocalSend) : débit proche du Wi-Fi, mais seulement entre applis natives ; WebRTC reste
  le seul moyen pour l'appli web.
- Reprise des envois après redémarrage de l'appli (aujourd'hui, la reprise suppose que
  l'appli soit restée ouverte : le fichier n'est gardé qu'en mémoire).
